# GhostClick

Движок автокликера для Windows на .NET 8: клики мышью и нажатия клавиш с настраиваемыми
режимами, точками клика и движением курсора.

Вся логика живёт в библиотеке `ClickerEngine.Core` без единой зависимости от UI. Сверху
подключается интерфейс: `GhostClick.App` — окно WPF с WebView2, внутри которого работает
веб-страница по дизайну GhostClick v3 (клавиатура и мышь, на которых назначаются горячие
клавиши и действия, док управления, выезжающая панель настроек). Рядом остался старый
dev-харнесс `ClickerEngine.DevUI` с прямым доступом ко всем полям профиля.

## Установка

Скачайте `GhostClick-Setup-<версия>.exe` со страницы
[Releases](https://github.com/Sergey5600/GhostClick/releases) и запустите. Установщик
ставит программу для текущего пользователя (права администратора не нужны), добавляет её
в меню «Пуск» и, если не снять галочку, на рабочий стол. Нужна 64-битная Windows 10 или 11;
.NET ставить не надо, а компонент Microsoft Edge WebView2 установщик при необходимости
поставит сам. Новая версия ставится поверх старой, профили сохраняются; удаление — через
**Параметры → Приложения**.

Установщик не подписан сертификатом, поэтому при первом запуске Windows SmartScreen может
показать «Система Windows защитила ваш компьютер» — **Подробнее → Выполнить в любом случае**.

## Ключевые архитектурные решения

### `IInputInjector` — единственный шов к ОС

Всё, что движок делает с системой, выражено пятью примитивами:

```csharp
public interface IInputInjector : ICursorProvider
{
    void MoveTo(ScreenPoint position);
    void MouseButtonDown(MouseButton button);
    void MouseButtonUp(MouseButton button);
    void KeyDown(VirtualKey key);
    void KeyUp(VirtualKey key);
}
```

Штатная реализация — `SendInputInjector` (user-mode `SendInput`). Если позже понадобится
альтернативный бэкенд (подписанный low-level драйвер, железный девайс, удалённый агент),
достаточно реализовать этот интерфейс — остальной код не меняется. В комплекте уже есть
`RecordingInputInjector`, который вместо реального ввода пишет журнал: на нём работают
тесты и режим «dry run» в dev-UI.

### План отделён от исполнения

`ActionPlanner` превращает профиль в **ленивый поток** примитивов `EngineStep`
(`Wait` / `MoveTo` / `MouseDown` / `MouseUp` / `KeyDown` / `KeyUp`). Бесконечный режим —
это буквально бесконечная последовательность; останавливает её движок, а не планировщик.

Из-за этого разделения весь движок тестируется без часов, потоков и Windows API: тест
просто перечисляет план и проверяет точную последовательность шагов.

### Часы и случайность инжектируются

`IClock` и `IRandomSource` — параметры конструктора. `VirtualClock` в тестах прогоняет
пятиминутный сценарий мгновенно, `ScriptedRandomSource` делает проверки дрожания точными,
а не статистическими.

## Возможности

### Хоткеи

Глобальные, работают вне фокуса окна. Реализованы через low-level хуки
(`WH_KEYBOARD_LL` + `WH_MOUSE_LL`), а не через `RegisterHotKey`, потому что нужны три вещи,
которых `RegisterHotKey` не умеет: боковые кнопки мыши (X1/X2), **отпускание** клавиши
(на нём держится режим Hold) и привязка «голых» клавиш.

* Любая клавиша или комбинация `Ctrl`/`Alt`/`Shift`/`Win` + клавиша, включая X1/X2.
* Отдельно: старт/стоп (`F6`), пауза (`F7`), экстренный стоп (`Ctrl+F12`), запись точки (`F9`).
* Если старт по хоткею невозможен (профиль не проходит проверку), `HotkeyController`
  сообщает об этом событием `StartRejected`, а не глотает исключение на фоновом потоке.
* Хуки живут на своём потоке с собственным насосом сообщений, а события поднимаются на
  **втором** потоке — поэтому обработчик может спокойно блокироваться (например, останавливать
  движок), не подвешивая очередь ввода системы и не рискуя тем, что Windows молча снимет хук
  по `LowLevelHooksTimeout`.
* Собственный инжектированный ввод отфильтровывается (`LLKHF_INJECTED` + метка в
  `dwExtraInfo`), так что кликер не может затриггерить сам себя.

### Режимы клика

* **Toggle** — старт/стоп по хоткею, клики с заданным интервалом.
* **Hold** — клики идут, пока клавиша зажата.
* Количество: фиксированное или бесконечно до повторного хоткея.
* Интервал с точностью 1 мс; опционально — случайный разброс `min–max`.
* Действие — это **список** (`ActionSettings.Inputs`): кнопки мыши (ЛКМ / ПКМ / СКМ / X1 / X2)
  и клавиши, каждая со своими модификаторами. На каждом такте всё нажимается одновременно,
  удерживается и отпускается в обратном порядке; модификаторы всех элементов оборачивают
  действие целиком. Это по-прежнему одно действие для счётчиков и лимитов.
* Одиночный или двойной клик, настраиваемое время удержания — фиксированное или случайное
  из диапазона (`RandomizeHoldDuration`, `Min/MaxHoldDurationMs`).

### Точки клика

* **CurrentCursor** — клик на месте, курсор не двигается вообще.
* **FixedPoint** — заданные координаты.
* **MacroRoute** — список точек по очереди, у каждой своя задержка (0 = общий интервал);
  точки можно временно выключать, не удаляя.
* **Directional** — непрерывный дрейф по углу с заданной скоростью, клики по пути.

Запись точки: навёл курсор → нажал хоткей → координата сохранена (`PointRecorder`).

### Движение мыши

* **Instant** — телепорт одним событием.
* **Smooth** — интерполяция с кривыми `Linear` / `EaseIn` / `EaseOut` / `EaseInOut`,
  длительность задаётся напрямую или выводится из скорости и расстояния. Последний сэмпл
  всегда точно попадает в цель — ни easing, ни дрожание не могут оставить курсор «недошедшим».
* **Directional** — угол 0–360° (0 — вправо, 90 — вверх), скорость в px/s, поведение
  у края экрана: `Stop` / `Bounce` / `Wrap` / `Restart`, плюс случайное блуждание угла.
  Позиция хранится с субпиксельной точностью, поэтому медленный дрейф (например 30 px/s
  шагами по 10 мс) реально движется, а не залипает на округлении.

### Рандомизация («антидетект»)

* Случайное смещение точки клика по X/Y. При клике «у курсора» смещение отсчитывается от
  точки, куда целился пользователь, а не от предыдущего смещения, — иначе курсор медленно
  уползал бы случайным блужданием.
* Дрожание промежуточных точек траектории.
* Случайное масштабирование всех пауз на ±N %.

Это меняет форму потока ввода. Скрыть от драйверного или ядерного наблюдателя тот факт,
что ввод синтетический, оно не может — см. ниже.

### Профили

JSON, по файлу на профиль, в `%APPDATA%\GhostClick`:

```
%APPDATA%\GhostClick\
├── settings.json          последний использованный профиль
└── profiles\
    ├── Default.json
    └── Fishing.json
```

Запись атомарная (через временный файл), enum'ы пишутся именами — файл читаемый и
правится руками. Последний использованный профиль загружается автоматически при старте.

Схема профиля — версия 2: действие описывается списком `inputs`. Файлы версии 1 (одна
кнопка или одна клавиша в полях `kind` / `button` / `key` / `keyModifiers`) при чтении
переводятся в список из одного элемента и ведут себя как раньше.

### Безопасность

* Экстренный стоп по хоткею (по умолчанию `Ctrl+F12`), работает в любом состоянии.
* Лимит длительности прогона (`MaxRunDurationSeconds`, у движка по умолчанию 10 минут) и
  лимит количества действий. В интерфейсе «Повтор: Бесконечно» снимает лимит длительности —
  такой прогон заканчивает только пользователь (или другие предохранители).
* Опционально: остановка, если пользователь сам увёл курсор от того места, где его ожидает
  движок, — от последней точки, куда он его поставил, а при клике «у курсора» — от места
  первого клика.
* «Шлюз окна» (`IWindowProbe`, реализация `Win32WindowProbe`): действие не начинается, пока
  оно ушло бы в окно самого кликера — можно нажать «Старт» в интерфейсе и спокойно навести
  мышь на цель: после такого ожидания цель должна продержаться под курсором ~300 мс
  (`WindowSettleTime`), чтобы клик не достался окну, над которым мышь просто пролетала.
  С `SafetySettings.ActiveWindowOnly` прогон дополнительно «привязывается» к окну первого
  действия и ждёт, пока ввод снова пойдёт в него. Клики судятся по окну под
  курсором, клавиши — по активному окну. В dry run шлюз молчит (`DryRunAwareWindowProbe`).
* Если прогон отменили между нажатием и отпусканием, зажатые кнопки и клавиши гарантированно
  отпускаются — иначе кнопка залипла бы на всю систему.
* Курсор возвращается туда, где был до старта (настраивается).

### Счётчики

`SessionStatistics`: действия, физические клики, нажатия клавиш, количество прогонов, общее
время работы. Двойной клик — это одно «действие» и два «клика».

## Использование Core

```csharp
using var host = ClickerHost.CreateDefault();

var profile = host.Start();          // грузит последний профиль и включает хоткеи
profile.Interval.DelayMs = 50;
profile.Action.Inputs = [InputChord.Mouse(MouseButton.Left), new InputChord(VirtualKey.E)];
host.ApplyProfile(profile);

host.Engine.Started += (_, e) => Console.WriteLine($"Старт: {e.Profile.Name}");
host.Engine.Stopped += (_, e) => Console.WriteLine($"Стоп: {e.Reason}, {e.ActionsPerformed} действий");

// Дальше всё крутится на хоткеях (по умолчанию F6 — старт/стоп, Ctrl+F12 — экстренный стоп),
// либо программно:
host.Engine.Start();
```

События движка поднимаются **на его собственном потоке**. UI обязан маршалить их сам;
в WPF — только через `Dispatcher.BeginInvoke`, не `Invoke`: `Stop()` блокирует вызывающий
поток в ожидании потока движка, и синхронный маршалинг дал бы взаимную блокировку.

Собрать всё вручную, если нужен свой набор компонентов:

```csharp
var screen = new Win32ScreenGeometry();
var injector = new SendInputInjector(screen);
var engine = new AutoClickerEngine(injector, new SystemClock(), screen, new SystemRandomSource());
```

## Сборка и запуск

Нужен .NET 8 SDK.

```bash
# всё решение (Windows)
dotnet build GhostClick.sln

# движок, мост и тесты — собираются на любой платформе
dotnet build src/GhostClick.Bridge/GhostClick.Bridge.csproj
dotnet test  tests/ClickerEngine.Core.Tests/ClickerEngine.Core.Tests.csproj
dotnet test  tests/GhostClick.Bridge.Tests/GhostClick.Bridge.Tests.csproj

# приложение (только Windows)
dotnet run --project src/GhostClick.App

# dev-харнесс (только Windows)
dotnet run --project src/ClickerEngine.DevUI
```

`GhostClick.App` и `ClickerEngine.DevUI` — WPF, поэтому собираются только там, где у SDK
есть компонент Windows Desktop, то есть на Windows или с официальным .NET SDK. На Linux с
пакетом `dotnet-sdk-8.0` из репозиториев дистрибутива этого компонента нет, и сборка всего
решения целиком там упадёт — движок, мост и тесты при этом собираются и проходят полностью.

Установщик собирает GitHub Actions (`.github/workflows/windows-build.yml`) на каждый пуш:
Windows-машина собирает всё решение, гоняет оба набора тестов, публикует приложение, пакует
его в `GhostClick-Setup-<версия>.exe` и прикладывает к запуску (вкладка **Actions** → нужный
запуск → **Artifacts**). Потом она проверяет установщик так, как его увидит пользователь:
тихо ставит, проверяет ярлыки и запись в «Приложениях», запускает установленную программу
и ждёт её интерфейс, удаляет и проверяет, что ничего не осталось, кроме профилей.

Приложению нужен Microsoft Edge WebView2 Runtime: в Windows 11 он встроен, в Windows 10
обычно уже установлен вместе с Edge. Установщик ставит его сам, если его нет; при запуске
без установщика приложение в этом случае предложит открыть страницу загрузки.

### Установщик

`installer/GhostClick.iss` — сценарий Inno Setup 6.3. Что он делает:

* ставит в `%LocalAppData%\Programs\GhostClick` без запроса прав администратора (как
  Discord или VS Code; `/ALLUSERS` в командной строке ставит в Program Files для всех);
* создаёт ярлык в «Пуске» и, по галочке (включена), на рабочем столе;
* ставит WebView2 Runtime с помощью встроенного загрузчика Microsoft, если его нет;
* закрывает запущенный GhostClick перед обновлением или удалением (мьютекс
  `GhostClick.SingleInstance` из `Program.cs`);
* при удалении стирает кэш интерфейса (`%LocalAppData%\GhostClick`), а про профили
  (`%AppData%\GhostClick`) спрашивает — по умолчанию оставляет.

Интерфейс мастера русский (английский — если Windows не русская), картинки слева и в шапке —
`installer/art/*.bmp` в пяти масштабах экрана, нарисованы из `assets/InstallerWizard.svg`
и иконки:

```bash
assets/build-installer-art.sh   # нужны librsvg2-bin, ImageMagick и установленный шрифт Geist
```

`AppId` в сценарии менять нельзя: по нему новая версия находит установленную.

**Выпуск версии.** Версия записана в `<Version>` в `src/GhostClick.App/GhostClick.App.csproj`.
Поднимите её, закоммитьте и отправьте тег с тем же номером:

```bash
git tag v1.0.0 && git push origin v1.0.0
```

CI соберёт и проверит установщик и создаст на GitHub релиз `GhostClick 1.0.0` с
`GhostClick-Setup-1.0.0.exe` — ссылку на него и можно раздавать. Тег, не совпадающий с
`<Version>`, сборка отклонит. Все остальные сборки получают версию вида `1.0.0-dev.<номер
запуска>`.

**Собрать вручную** на Windows с .NET 8 SDK и [Inno Setup 6.3](https://jrsoftware.org/isdl.php):

```
dotnet publish src/GhostClick.App -c Release -r win-x64 --self-contained true -p:DebugType=none -p:PublishDocumentationFiles=false -o publish/app
curl -L -o installer/MicrosoftEdgeWebview2Setup.exe https://go.microsoft.com/fwlink/p/?LinkId=2124703
ISCC installer/GhostClick.iss /DAppVersion=1.0.0
```

Готовый установщик появится в `publish/installer`.

### Интерфейс (`GhostClick.App`)

Вариант A из дизайн-хэндоффа: окно WPF целиком занято WebView2, а интерфейс — обычная
страница в `src/GhostClick.App/wwwroot` (Preact + htm без сборки, шрифты Geist и Geist Mono
лежат локально, сеть не нужна). Страница отдаётся с виртуального хоста
`https://ghostclick.example/`, навигация куда-либо ещё запрещена, браузерные сочетания
(F5, F12, Ctrl+P…), зум и автозаполнение выключены.

Разделение ответственности:

* **Страница** владеет редактированием: держит видимый срез профиля, применяет правила
  назначений (клавиша принадлежит одному назначению, ЛКМ без модификатора нельзя сделать
  горячей клавишей, действия переключаются) и после каждого изменения отправляет срез
  целиком.
* **`GhostClick.Bridge.UiBridge`** владеет всем, что должно быть правдой вне страницы:
  профиль движка, хоткеи, сохранение, флаг несохранённых изменений, счётчики прогона,
  журнал. Пока страница ждёт клавишу для назначения, хоткеи (кроме экстренного стопа)
  отключены, чтобы F6 не запустил кликер посреди назначения.

Протокол — JSON-сообщения через `chrome.webview`:

| Направление | Сообщения |
| --- | --- |
| страница → движок | `ready`, `start`, `stop`, `pause`, `resume`, `panic`, `setProfile {data}`, `saveProfile`, `revertProfile`, `loadProfile {name}`, `newProfile`, `duplicateProfile`, `setDryRun {value}`, `listen {value}` |
| движок → страница | `init`, `profile`, `dirty`, `state` (4 раза в секунду во время прогона), `log`, `toast`, `pointAdded`, `hotkey` |

Клавиши называются по `KeyboardEvent.code` (`KeyQ`, `Digit1`, `F6`…), кнопки мыши —
`Mouse1`…`Mouse5` (4 = X1, 5 = X2); соответствие с `VirtualKey` — в `KeyCodes`.

**Превью без Windows.** Если открыть `wwwroot/index.html` в обычном браузере (через любой
статический сервер, например `python -m http.server` в этой папке), страница не найдёт
WebView2 и подключится к встроенному эмулятору с тем же протоколом: профили в памяти,
симуляция кликов, горячие клавиши работают, пока вкладка в фокусе. Так интерфейс можно
смотреть и проверять на любой машине.

Отличия от прототипа дизайна, сделанные намеренно:

* Закрытая панель настроек уезжает за край полностью (в прототипе её край выглядывал на 12 px).
* На клавишах шириной 1u длинная метка назначения («ТОЧКА», «СТАРТ») заменяет русскую
  букву — вместе они не помещаются и налезали друг на друга.
* Выбор нового назначения сразу показывает его подсказку, не дожидаясь, пока погаснет
  уведомление о предыдущем.
* Удерживание физического модификатора не мигает «ожидающим» модификатором из-за автоповтора.
* Колесо и боковые кнопки мыши в режиме ожидания можно нажать физически; ЛКМ и ПКМ
  выбираются на рисунке, потому что ими управляют самой страницей.
* Потеря фокуса окном завершает режим ожидания: хоткеи снова работают, когда вы ушли в игру.
* «В секунду» — измеренная частота за последние две секунды, а не расчёт из интервала.
* Пояснения к переключателям безопасности сверены с движком: каждое теперь соответствует
  реальной настройке (`PositionJitterEnabled`, `RandomizeHoldDuration`,
  `StopOnUserCursorMove`, `ActiveWindowOnly`).

Новые профили из интерфейса создаются с включёнными джиттером, случайным удержанием и
«Только активное окно» (`UiDefaults`), как в макете.

«Повтор: Бесконечно» значит «до остановки»: интерфейс не показывает лимит длительности
прогона, поэтому движок получает копию профиля без этого лимита
(`ProfileMapper.ToEngineProfile`). Сам профиль лимит не теряет: переключение «Бесконечно» →
«N раз» возвращает всё как было, а с «N раз» действует лимит, записанный в профиле (например,
заданный в dev-харнессе). Это касается и профилей, сохранённых раньше с лимитом в 10 минут:
при «Бесконечно» они работают без него и не помечаются изменёнными. Новые профили из
интерфейса создаются вообще без лимита.

### Иконка

Исходник — `assets/AppIcon.svg`, готовый многоразмерный `assets/AppIcon.ico` рядом. Его
берут оба приложения, `GhostClick.App` и dev-харнесс, двумя путями: через
`<ApplicationIcon>` (иконка самого `.exe` — панель задач, проводник, Alt-Tab, закреплённые
ярлыки) и через `Window.Icon` (заголовок окна, в том числе при запуске `dotnet run` по dll).

Внутри 9 кадров: 16, 20, 24, 32, 40, 48, 64, 128 и 256 px. 16/32/48/256 нужны оболочке,
остальные закрывают масштабирование экрана 125–200 %. Пересобрать после правки SVG:

```bash
assets/build-icon.sh        # нужны librsvg2-bin и ImageMagick
```

Каждый размер рендерится прямо из вектора, а не уменьшается из одного большого растра:
librsvg считает тень на целевом разрешении, и на 16 и 32 px — там, где иконка проводит
большую часть жизни — результат заметно чётче.

### Dev-харнесс

Одно окно со всеми настройками профиля, глобальными хоткеями, журналом событий и строкой
состояния (состояние движка, счётчики, текущий бэкенд ввода, позиция курсора). Отдельно
стоит галочка **Dry run**: ввод никуда не уходит, но в журнале видно точный поток событий,
который сгенерировал бы профиль. Удобно проверять маршруты и сглаживание, не гоняя мышь
по экрану.

Это именно строительные леса: чистый code-behind, никакого MVVM, всё общение с движком идёт
через `ClickerHost`. Настоящий интерфейс теперь — `GhostClick.App`; харнесс оставлен ради
настроек, которых в интерфейсе нет (фиксированная точка, направленный дрейф, кривые
сглаживания, лимиты). Действие он редактирует как один элемент — первый в списке
`Inputs`, остальные не трогает. Когда он станет не нужен, достаточно удалить проект.

## Совместимость с играми

Основной метод — `SendInput`. Он работает в большинстве обычных игр без ядерного анти-чита.
Несколько деталей реализации сделаны именно ради этого:

* клавиатура отправляется **скан-кодами** (`KEYEVENTF_SCANCODE`), а не только виртуальными
  клавишами — иначе игры, читающие raw input или DirectInput, часто просто игнорируют событие;
* перемещения абсолютные по всему виртуальному рабочему столу, с `MOUSEEVENTF_MOVE_NOCOALESCE`,
  чтобы система не склеивала частые шаги плавного движения;
* dev-UI объявляет per-monitor DPI awareness — без этого Windows виртуализирует метрики
  экрана, и записанные координаты не совпали бы с теми, куда реально уходит клик.

**Ограничение, которое нельзя обойти на этом уровне.** Игры с ядерным анти-читом
(BattlEye, EasyAntiCheat, Vanguard и т. п.) с высокой вероятностью всё равно детектят
программный ввод: он приходит без физического HID-устройства и помечен системой как
инжектированный (`LLMHF_INJECTED`), что видно любому наблюдателю уровня драйвера. Это
фундаментальное свойство подхода, а не недоработка реализации; рандомизация таймингов и
координат меняет статистику, но не природу событий. Именно поэтому метод ввода вынесен
за интерфейс `IInputInjector` — если понадобится другой уровень, меняется одна реализация.

**UIPI.** Если целевое окно запущено с повышенными правами, а кликер — нет, Windows
отбросит инжектированный ввод. `SendInputInjector` в этом случае бросает
`InputInjectionException` вместо тихого клика в никуда: движок останавливается с
`StopReason.Error`, и причина видна. Лечится запуском кликера от администратора.
